# Ivory Tower V1 development contract

## Toolchain

Ivory Tower development and CI use Node 24.16.0 and npm 11.13.0. The root
Theia engine declaration remains `>=22` for upstream compatibility; the pinned
Ivory toolchain is recorded in `.nvmrc` and `configs/ivory-toolchain.json`.
The monorepo uses Lerna 10 as an intentional fork pin until Eclipse Theia
upgrades; do not revert it to 9 during upstream merges.

On Windows PowerShell, use `npm.cmd`:

```powershell
npm.cmd ci
npm.cmd run check:ivory-install
npm.cmd run verify:ivory-tower
```

On Ubuntu or another Unix shell, use `npm`:

```sh
npm ci
npm run check:ivory-install
npm run verify:ivory-tower
```

`format:write:ivory-tower` is developer-invoked. CI only runs
`format:check:ivory-tower`; it never rewrites files. The pinned Prettier
configuration applies only to `packages/ivory-tower-*` and
`examples/ivory-tower-browser`.

## Environment

Copy `.env.example` to the local environment and set `DATABASE_URL` before
starting the API or worker. `readIvoryTowerEnvironment(role)` validates the
database, queue, storage, provider, Docling, browser, role, and
`configs/ivory-deployment-profiles.json` combination before startup. Local
development may use filesystem objects and documented local defaults; staging
and production require S3-compatible storage, both access-key secrets, and
reject example MinIO/postgres credentials.

`/health/live` is a liveness ping. `/health/ready` returns per-check JSON
(postgres, schema, queue, object store, Docling). The API is ready without
Docling; a failed required check is HTTP 503. The browser health view still
uses `fetch(.../health/ready).ok` and reports `ok`, `degraded`, or
`unavailable`; it does not claim readiness from a static UI flag.

Secrets are environment-injected. Runtime logs, Sentry, and audit-shaped
payloads share `redactSecrets` / `logIvoryError`. `npm run secret:scan` is the
IV-19 repository scan and does not cover that runtime boundary. See
`docs/iv-22-deployment-secrets.md` (IV-22).

## Architecture rules

The allowed dependency direction is:

```text
contracts -> domain -> application -> adapters -> infrastructure / api / worker
health browser -> application contracts only
```

Provider, database, Graphile Worker, Docling, Theia, and LiqUIdify clients stay
behind the appropriate adapter or application boundary. The boundary checker
also runs negative fixtures for those prohibited imports. The browser
application does not load a runtime plugin host.

## Required commands

- `npm run verify:ivory-tower` — the local and CI gate.
- `npm run check:ivory-install` — pinned toolchain plus linked `@theia/ext-scripts` bootstrap
  preflight; run immediately after `npm ci`.
- `npm run compile:ivory-services` — compile `@ivory-tower/api` and `@ivory-tower/worker`
  (and their dependencies) so `start:ivory-api` / `start:ivory-worker` have `lib/start.js`.
- `npm run verify:ivory-session-04` — clean Docker runtime, immediate N-1 migration
  snapshot/restore/upgrade, object-store reconciliation, and API/worker/Docling proof.
- `npm run typecheck:ivory-tower` — scoped compile/typecheck.
- `npm run format:check:ivory-tower` — pinned first-party formatting check.
- `npm run format:write:ivory-tower` — explicit developer formatting.
- `npm run dependency:policy` — licence classes, the reviewed dependency inventory,
  quality scope, image pinning, the exception register, and the adversarial fixtures.
- `npm run secret:scan` — sentinel and credential scan.
- `npm run test:ivory-browser` — the health-view Playwright test.

Release evidence, generated by CI rather than by the local gate:

- `npm run sbom:generate` — CycloneDX SBOMs for the source tree and each deployable,
  into `artifacts/sbom/`.
- `npm run notices:generate` — deterministic third-party notices, into `artifacts/notices/`.

`artifacts/` is gitignored; the CI `governance` job uploads it. Dependency governance is
documented in `docs/iv-19-dependency-governance.md` (IV-19). Deployment profiles,
structured readiness, and runtime secret redaction are documented in
`docs/iv-22-deployment-secrets.md` (IV-22).

The Session 04 runtime verifier removes only the checkout-owned `.ivory-tower/` state
directory, deleting root-owned bind-mount children through the digest-pinned Postgres image.
It is a disposable local proof, never a production reset or rollback mechanism.
See `docs/iv-21-local-runtime.md` (IV-21) for exact operational sequencing and failure
evidence.

The aggregate gate runs the install bootstrap, boundaries, compile, lint, package tests, production
browser build, browser tests, dependency policy, secret scan, `git diff --check`,
and a clean-tree assertion. Run it from a clean checkout when validating CI parity.

The Ivory quality scopes cover every workspace named `@ivory-tower/*` **or**
`@theia/ivory-*`, so `@theia/ivory-identity` participates in formatting, compile,
lint, test, and dependency gates. `npm run dependency:policy` fails if any
Ivory-owned package falls outside those scopes.

## Docling pin and supported registry

The supported V1 image is the Quay manifest list below:

```text
quay.io/docling-project/docling-serve:v1.21.0@sha256:32b3de41f325f93c1dd35907cd9147fa35df9f7c5abc86eb2788b6bda7ce6d10
```

GHCR publishes the same project image and is the supported mirror. A mirror
may replace Quay only after resolving the same `v1.21.0` manifest list and
recording the mirror digest in the deployment evidence. Mutable tags and
unverified mirrors are rejected by environment validation.

## Troubleshooting

- `EPERM` under the npm cache: retry with the managed Windows approval path or
  use a writable npm cache; do not loosen dependency pins.
- Boundary failures: run `npm run check:ivory-boundaries` and inspect the
  prohibited import plus its layer before changing a package dependency.
- A missing `DATABASE_URL`, S3 secret, or mutable `DOCLING_IMAGE` is a startup
  configuration failure, not a readiness warning.
- If Docker Desktop is unavailable, the deterministic package/runtime tests
  remain runnable, but the PostgreSQL/MinIO/Docling integration gate is not
  complete until `npm run verify:ivory-session-04` (or the Ubuntu Session 04 CI
  job) has passed.
- If `@theia/ext-scripts/bin/theia-ext.js` is missing, run the pinned `npm ci`
  from the repository root. Do not copy the binary into `node_modules`;
  `check:ivory-install` must pass before any Ivory compile or test result is
  meaningful.
- The inherited Electron target is a compatibility gate only. It is not the
  Ivory Windows product until the Phase 7 wrapper and Acrylic adapter exist.
